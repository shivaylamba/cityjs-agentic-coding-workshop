# 01 · Give the agent a working agreement

09:10–09:25 · 15 minutes

Start an empty repository, define the project boundary, and prove the agent can find the instructions.

## Concepts

A coding agent is a model operating inside a harness: the harness supplies file access, commands, tools and an execution loop. A polished answer is a proposal until its changes and checks are inspected.

Context engineering means selecting the useful facts for this task: goal, constraints, relevant files, commands and evidence. It does not mean pasting the entire repository into every message.

Keep stable project rules in AGENTS.md. Keep one-task requirements in the spec or prompt. A Markdown instruction is guidance; an actual permission setting controls which actions the tool can execute.

## Steps

### 1. Create the workspace

Use a new folder, not the TanStack storefront repo. These commands work in a terminal; PowerShell users can create the folder and files in their editor.

```sh
mkdir cityjs-session-planner
cd cityjs-session-planner
git init -b main
mkdir docs
mkdir src
```

### 2. Write only the useful context

Create AGENTS.md using the downloadable working-agreement template. Change one rule yourself: define either a forbidden dependency or a required accessibility behaviour. Create CLAUDE.md containing @AGENTS.md on its own line. No application code yet.

### 3. Open one agent

Launch Codex or Claude Code in this folder. Confirm the working directory and normal permission settings. Ask it to read your working agreement, explain what it may edit, and wait. Use a second fresh conversation to check that the agreement is discovered.

```sh
codex
# Or, in a separate choice of client:
claude
```

### 4. Capture the baseline

Save one vague request, the first response and your missing requirements in docs/learning-log.md. Do not accept a giant implementation from the vague prompt. Commit the context files after you inspect them.

```sh
git add AGENTS.md CLAUDE.md docs
git commit -m "Define workshop working agreement"
```

## Editable task prompt

```text
Read the applicable project instructions and list their paths. Summarise the app purpose, explicit non-goals, verification commands and actions that need a separate release decision. Do not create application code. Identify three questions a vague request to "build a conference planner" leaves unanswered. Return facts separately from assumptions.
```

## Evidence

- A fresh conversation identifies AGENTS.md and the intended project root.
- The agreement says this app is a fictional personal planner, not a seat booking service.
- No API key, private account data or deployment permission is stored in project instructions.

## Experiment

Remove a single task detail from the prompt and keep it in AGENTS.md. Start a fresh conversation. Does the agent find it? Inspect the file-loading evidence your client provides; a confident restatement alone is weaker evidence.

## Recovery

If instruction discovery fails, explicitly attach/open AGENTS.md in the client and label that run as manually supplied context. Check your launch directory and nested overrides. Do not edit your global instruction files during this workshop.
