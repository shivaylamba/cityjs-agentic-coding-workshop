# 01 · Give the agent a working agreement

09:10–09:25 · 15 minutes

Start an empty repository, define the project boundary, and prove the agent can find the instructions.

## Concepts

A coding agent is a model operating inside a harness: the harness supplies file access, commands, tools and an execution loop. A polished answer is a proposal until its changes and checks are inspected.

Context engineering means selecting the useful facts for this task: goal, constraints, relevant files, commands and evidence. It does not mean pasting the entire repository into every message.

Keep stable project rules in AGENTS.md. Keep one-task requirements in the spec or prompt. A Markdown instruction is guidance; an actual permission setting controls which actions the tool can execute.

## Understand before building

### What is a coding agent, and what is context?

A model generates suggestions. The harness is the software that lets it read files, edit code and run tools. A coding agent combines the model with that action loop. Context is the information available for its current decision; opening a new chat does not mean it automatically knows every previous decision.

```text
Goal → read applicable instructions → inspect files → propose/edit → run checks → inspect result
```

In our planner, the goal might be preventing clashes. The agent needs the scheduling rule and relevant code, not unrelated chat history. Tool results are observations; a confident sentence alone is not a test result.

**Check your understanding:** Why does a new conversation need project context?

**Expected reasoning:** It needs an explicit, discoverable source for project rules instead of relying on a previous conversation.

### What is AGENTS.md?

AGENTS.md is an ordinary Markdown file of instructions for coding agents working in a project. It does not create an agent or execute code. Put it at the root of your workshop project. Codex discovers applicable instructions; nested overrides and client settings can affect what loads, so verify the active instructions.

```text
# Project instructions
Build a fictional CityJS planner with React and TypeScript.
- Do not claim to reserve real seats.
- Keep scheduling rules separate from React.
- Run relevant checks after changing code.
- Report failed or unrun checks honestly.
```

The heading names its purpose. The first sentence fixes the stack and product. The next lines constrain product claims, code organisation and evidence. None is a technical permission setting: the client still controls tool access.

**Check your understanding:** Which rule would you add for keyboard users?

**Expected reasoning:** For example: every interactive control must have an accessible label and work from the keyboard.

### README, instructions, spec and learning log

README.md explains setup and use to people. AGENTS.md describes stable working rules for agents. docs/spec.md will describe product behaviour. docs/plan.md will describe implementation tasks. docs/learning-log.md is your record of decisions and observed results; it is our convention, not a file every agent automatically loads.

```text
cityjs-session-planner/
  AGENTS.md
  CLAUDE.md
  docs/
    learning-log.md
```

CLAUDE.md contains @AGENTS.md for this workshop’s shared-instructions compatibility path. Supported Claude versions may also discover AGENTS.md directly; inspect your client rather than assuming identical discovery. Copy template contents to the actual filenames: AGENTS.md.txt is a downloadable example, not the intended active name.

**Check your understanding:** Should today’s one-off export request live permanently in AGENTS.md?

**Expected reasoning:** Keep the stable checking rules there; put the export behaviour in the spec and selected task.

### Commit, push and a fresh conversation

A commit is a local snapshot of selected changes. A push sends commits to a remote. Lab 01 needs only a local commit. A fresh agent conversation tests whether instructions are discoverable independently of the earlier chat.

```text
git status --short
git add AGENTS.md CLAUDE.md docs
git commit -m "Define workshop working agreement"
```

Status shows changed files. Add stages the intended files. Commit records them locally; it does not upload anything. Ask the new agent to identify instruction paths and show the client’s file-loading evidence when available.

**Check your understanding:** Does writing “do not deploy” replace permission controls?

**Expected reasoning:** No. It expresses a working rule; inspect the client’s actual permissions separately.

## Steps

### 1. Create the workspace

Use a new folder, not the TanStack storefront repo. These commands work in a terminal; PowerShell users can create the folder and files in their editor.

```sh
mkdir cityjs-session-planner
cd cityjs-session-planner
git init -b main
mkdir docs
mkdir src
```

### 2. Write only the useful context

Create AGENTS.md using the downloadable working-agreement template. Change one rule yourself: define either a forbidden dependency or a required accessibility behaviour. Create CLAUDE.md containing @AGENTS.md on its own line. No application code yet.

### 3. Open one agent

Launch Codex or Claude Code in this folder. Confirm the working directory and normal permission settings. Ask it to read your working agreement, explain what it may edit, and wait. Use a second fresh conversation to check that the agreement is discovered.

```sh
codex
# Or, in a separate choice of client:
claude
```

### 4. Capture the baseline

Save one vague request, the first response and your missing requirements in docs/learning-log.md. Do not accept a giant implementation from the vague prompt. Commit the context files after you inspect them.

```sh
git add AGENTS.md CLAUDE.md docs
git commit -m "Define workshop working agreement"
```

## Editable task prompt

```text
Read the applicable project instructions and list their paths. Summarise the app purpose, explicit non-goals, verification commands and actions that need a separate release decision. Do not create application code. Identify three questions a vague request to "build a conference planner" leaves unanswered. Return facts separately from assumptions.
```

## Evidence

- A fresh conversation identifies AGENTS.md and the intended project root.
- The agreement says this app is a fictional personal planner, not a seat booking service.
- No API key, private account data or deployment permission is stored in project instructions.

## Experiment

Remove a single task detail from the prompt and keep it in AGENTS.md. Start a fresh conversation. Does the agent find it? Inspect the file-loading evidence your client provides; a confident restatement alone is weaker evidence.

## Recovery

If instruction discovery fails, explicitly attach/open AGENTS.md in the client and label that run as manually supplied context. Check your launch directory and nested overrides. Do not edit your global instruction files during this workshop.
