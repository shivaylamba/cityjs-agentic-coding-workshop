# 02 · Turn a vague idea into an executable spec

09:25–09:45 · 20 minutes

Write acceptance criteria, challenge assumptions, and split the project into a dependency-aware plan.

## Concepts

Spec-driven development makes product behaviour inspectable before implementation. A useful spec contains examples, edge cases and non-goals; a long feature wish list is not enough.

An acceptance criterion describes observable behaviour. “No time clashes” becomes an interval rule and examples. We treat each session as a half-open interval: the start is included and the end is excluded.

A task graph distinguishes prerequisites from independent work. A shared Session type comes before parallel feature work. Two agents writing App.tsx at the same time is not useful task decomposition.

## Understand before building

### Specification versus prompt versus plan

A specification records observable product behaviour. A task prompt delegates one selected piece of work. A plan orders the work and names dependencies. These documents are workshop conventions, not special executable files.

```text
Requirement: prevent agenda clashes.
Example: 09:00–09:30 + 09:30–10:00 → allow.
Example: 09:00–09:31 + 09:30–10:00 → reject.
Task: implement only add/remove and conflict protection.
```

The broad requirement is ambiguous. The examples remove a boundary ambiguity. The task authorises one slice of the spec; it does not authorise implementing every future feature.

**Check your understanding:** Can “make it user-friendly” be our only acceptance criterion?

**Expected reasoning:** No. Name an observable outcome, such as a visible clash message that leaves the agenda unchanged.

### Acceptance criteria, fixtures and non-goals

Acceptance criteria describe what must be demonstrably true. A fixture is fixed sample data used to make examples repeatable. A non-goal states what this application will not attempt. AC1–AC8 are labels so a task and test can point to the same requirement.

```text
AC2: A rejected duplicate leaves the agenda unchanged.
AC3: Back-to-back sessions are allowed.
Non-goal: no real seat reservations.
Fixture: materials/reference/src/sessions.ts
```

Use the fixture from the materials as data, not the entire completed app as a starter. Keep stable IDs and times. Each pair chooses the conflict message and empty-agenda presentation; those are actual product decisions.

**Check your understanding:** What could a test assert after rejecting a clash?

**Expected reasoning:** The error is visible and the set of selected session IDs is unchanged.

### Half-open intervals, explained with a clock

We include the start of a session and exclude its endpoint when comparing intervals. This allows the next session to start at that endpoint. Two sessions clash only if each starts before the other ends. Invalid intervals must be rejected separately.

```text
a.startMinute < b.endMinute
  && b.startMinute < a.endMinute
```

The first comparison asks whether A begins before B finishes. The second asks whether B begins before A finishes. Both must be true. Strict < allows touching endpoints; <= would treat that boundary as a clash.

**Check your understanding:** Does changing the room make two overlapping talks attendable?

**Expected reasoning:** No. The conflict belongs to one person’s time, regardless of room.

### Dependencies and the smallest approved slice

A dependency must be ready before another task can rely on it. Stable Session and feature-prop types are prerequisites for independent workers. A vertical slice is one complete user journey through the relevant layers.

```text
Shared types → core agenda → checkpoint
                          ↘ filters
                          ↘ favorites
filters + favorites → integration → export
```

The plan reserves App.tsx for one integrator. Filters and favorites can then have distinct ownership. In this lab ask for a plan only; authorise the first slice after reviewing it.

**Check your understanding:** Which file ownership would make parallel work risky?

**Expected reasoning:** Both workers independently editing App.tsx or changing shared props without agreement.

## Steps

### 1. Choose the product behaviour

Read the supplied project brief and fixture. Write docs/spec.md with criteria AC1–AC8. Decide how conflict errors appear and how the empty agenda looks. Annotate the two decisions you made yourselves.

### 2. Translate one rule into examples

Document that 09:00–09:30 and 09:30–10:00 may both be selected; 09:00–09:31 and 09:30–10:00 may not. A zero-length or reversed interval is invalid. A full session cannot be added. Existing selections cannot be duplicated.

### 3. Ask for a plan and challenge it

Use a read-only/planning mode if available, or explicitly request a plan only. Separate scaffolding, domain rules, UI, filters, favorites, export, review and release. Require a small integration seam for features/Filters.tsx and features/Favorites.tsx.

### 4. Freeze a small first slice

Approve only catalog, add/remove, conflict protection and local persistence for lab 03. Filters and favorites wait for lab 05; export waits for lab 06. Save the plan and one decision record.

```sh
git add docs
git commit -m "Approve planner acceptance criteria and task graph"
```

## Editable task prompt

```text
Read AGENTS.md and docs/spec.md. Do not edit code. First list ambiguities and decide which require my product decision. Then propose a dependency-ordered implementation plan with acceptance IDs, expected files, validation and risks per task. Keep filters and favorites independent behind typed props; reserve App.tsx and shared types for one integrator. We have a three-hour workshop. Propose the smallest first working slice and stop for review.
```

## Evidence

- At least eight acceptance criteria map to observable tests or browser actions.
- Back-to-back, overlapping, full and duplicate sessions have explicit expected results.
- The plan names dependencies, two non-overlapping ownership areas, and an integration owner.

## Experiment

Give the agent a contradictory requirement: “let me attend any two sessions” alongside “reject overlaps.” Ask it to identify the conflict without silently rewriting either rule. Then remove the contradiction and commit the resolved decision.

## Recovery

Use the supplied spec as a recovery aid, then change one acceptance example yourself and ask the agent to adapt the plan. Guided completion still requires explaining the decision and showing the corresponding check.
