# 03 · Build one verified React slice

09:45–10:10 · 25 minutes

Scaffold the app, implement the smallest end-to-end flow, and verify a real user journey.

## Concepts

A vertical slice crosses the relevant layers: input, domain rule, state update and visible result. Building all components before testing the journey hides integration mistakes.

The first deliverable is a session list and a persistent personal agenda. There is no runtime LLM call in this application. Codex or Claude is the development collaborator, not an in-app chatbot.

The check contract is npm run typecheck, npm test, npm run build, and npm run test:e2e. The agent must create these scripts, and a green exit must represent checks that actually ran.

## Understand before building

### Scaffolding and a vertical slice

Scaffolding creates the project structure, dependencies and scripts. React renders the interface, TypeScript checks types and Vite serves/builds the frontend. The slice connects a click to a domain decision, state update and visible result.

```text
Click Add → validate session → reject OR update agenda → render feedback
Refresh → read stored IDs → validate them → restore safe state
```

Domain functions belong outside React so they can be tested directly. React state drives the displayed agenda. Storage is another boundary: parsed data may be corrupt or stale and must be checked before use.

**Check your understanding:** Why not build all the visual components first?

**Expected reasoning:** A complete small journey exposes integration errors sooner than a collection of unconnected screens.

### What each check proves

Different checks answer different questions. Type checking catches incompatible program shapes; unit tests exercise selected rules; a build produces deployment assets; browser tests exercise real page interactions. None alone proves all behaviour.

```text
npm run typecheck  # TypeScript checks
npm test           # domain assertions
npm run build      # production assets
npm run test:e2e   # browser journey
npm run check      # first three, via real scripts
```

Inspect package.json: the script names are our agreed contract, not built-in guarantees. A script that only prints “passed” proves nothing. Keep browser tests at one worker. Use the dev server’s printed URL, not an assumed localhost port.

**Check your understanding:** Does a passing build prove reload persistence?

**Expected reasoning:** No. Observe reload in the browser and assert it in the relevant browser test.

### Local persistence and evidence

Browser-local storage belongs to an origin and browser profile. It is not cloud sync. Reading, parsing or writing it can fail. A rejected selection must not be persisted as if it succeeded.

```text
Observe: add → clash rejected → consecutive add → reload → remove
Also inspect: corrupt stored JSON → usable page, safe fallback
```

Check the visible agenda after each operation. Ask the agent for executed commands and results, then independently inspect a test and the browser journey. The full reference includes a storage-error case for recovery and inspection.

**Check your understanding:** What should happen if storage is unavailable?

**Expected reasoning:** The current visit should remain usable with honest feedback; do not promise persistence that failed.

### Diff, commit and tag

A diff shows changed lines. A commit records the selected snapshot. A tag names a checkpoint commit. These let later work start from a known base without replacing your files with another exercise starter.

```text
git diff
git diff --check
git add .
git commit -m "Build and verify the core planner"
git tag checkpoint-03
```

Read unexpected files before staging everything. diff --check catches whitespace problems, not application correctness. The tag will not include uncommitted edits; save and validate the intended slice first.

**Check your understanding:** What would invalidate the evidence you just collected?

**Expected reasoning:** Changing the relevant code or configuration afterward without checking the new candidate.

## Steps

### 1. Implement the approved first slice

Ask the agent to scaffold React + TypeScript + Vite, use the fixture, implement the domain rules, add/remove agenda entries and safe local persistence, and create the check scripts. Keep the lockfile. Do not implement the later feature tasks yet.

### 2. Inspect before trusting

Read package.json scripts, the domain function and one test. Open the generated README. Ask the agent to report executed commands, exit codes, failing checks and limitations. Independently run the checks.

```sh
npm run typecheck
npm test
npm run build
npm run dev -- --host 127.0.0.1
```

### 3. Verify the user journey

In the browser: add Opening the agent loop; reject Concurrent choices; add the back-to-back Spec clinic; reload; remove a session; verify a full session is refused. Observe the visible agenda after each action.

### 4. Checkpoint the slice

Run the browser test after installing its browser during prework. Commit only after inspecting the diff. Tag this local checkpoint so later branches share a known base.

```sh
npm run test:e2e
git diff --check
git add .
git commit -m "Build and verify the core planner"
git tag checkpoint-03
```

## Evidence

- A browser journey verifies add, rejected overlap, allowed back-to-back selection, reload and removal.
- Malformed local storage does not crash the page; restored unknown/full/overlapping selections are rejected or repaired.
- Tests exercise domain behaviour rather than merely copying the implementation.
- The first slice has a clean commit and checkpoint-03 tag.

## Experiment
