# 05 · Run parallel work without shared-file chaos

10:40–11:05 · 25 minutes

Build filters and favorites on independent branches, then integrate and validate both together.

## Concepts

A branch names a line of history. A worktree is a separate checkout. Two chats editing one folder still share files even if their prompts say “work independently.”

Each worker gets a task contract: goal, owned files, frozen interfaces, checks and a return format. File isolation reduces collisions; it does not remove logical integration bugs.

We use at most two worker sessions, no nested delegation and one browser-test worker. On a small laptop, run the tasks sequentially or split them across the pair. The integration lesson is the same.

## Understand before building

### Branch, worktree and session are different

A branch names a line of Git history. A worktree is a separate directory checked out on a branch. An agent session is a conversation/process. Two sessions in one directory can still overwrite each other’s files.

```text
cityjs-session-planner/  → main; integration owner
cityjs-filters/          → feat/filters; worker A
cityjs-favorites/        → feat/favorites; worker B
```

Create the worktrees from the committed parallel-base. They do not copy unsaved changes automatically. Separate directories isolate edits, but they are not security sandboxes and still use host resources.

**Check your understanding:** Can two chats safely edit App.tsx just because they have different tasks?

**Expected reasoning:** No. Separate checkouts and agreed ownership are needed; logical integration still needs review.

### Interfaces are agreements between workers

A typed interface says what data a component receives and what callbacks it may call. Freezing the props lets workers implement separate components without guessing the parent’s needs.

```text
Filters: { value: FilterValue; onChange(next): void }
Favorites: { count: number; only: boolean; onOnlyChange(next): void }
Integrator owns: App.tsx, shared types, stored IDs, package files
```

Filter changes report query/room to the parent. Favorites controls report the only-favorites flag; the integrator owns per-card toggles and persisted favorite IDs. If a prop needs changing, return a proposal to the integrator first.

**Check your understanding:** Why forbid both workers from changing package-lock.json?

**Expected reasoning:** Concurrent dependency changes introduce shared ownership and make the merge harder to reason about.

### Merge is text integration, checks are behaviour integration

Merge combines branch histories. Git can report a clean merge even if two individually valid features compose incorrectly. Search, room and favorites-only must all apply together, with AND semantics.

```text
git merge --no-ff feat/filters
git merge --no-ff feat/favorites
# Review and wire parent components.
npm run check
npm run test:e2e
```

Inspect worker commits before merging. If a conflict appears, resolve it deliberately or use git merge --abort to abandon that merge. Then test combined filters and the old agenda rules. Run workers sequentially if memory is constrained.

**Check your understanding:** What should happen if a favorite is in a different room from the chosen filter?

**Expected reasoning:** It should remain hidden while that room filter applies; favorites-only does not override the other filters.

## Steps

### 1. Make a clean shared base

Commit the current first slice, Skill and plan before creating worktrees. Verify status is clean. Leave the original checkout as the integration owner.

```sh
git status --short
git add .
git commit -m "Prepare independent feature contracts"
git tag parallel-base
git worktree add -b feat/filters ../cityjs-filters parallel-base
git worktree add -b feat/favorites ../cityjs-favorites parallel-base
git worktree list
```

### 2. Assign non-overlapping work

Worker A owns src/features/Filters.tsx and a filter helper/test. Worker B owns src/features/Favorites.tsx and a favorite helper/test. Both may read shared types. Only the integrator edits App.tsx. Share dependency installation only through normal package caching; do not let workers race on package-lock.json.

### 3. Collect two reviewable commits

Use one agent session per worktree. Ask each to report branch, changed files, acceptance IDs, actual checks and outstanding integration. Inspect before committing. A low-memory alternative is A then B; record that parallel execution was not attempted.

### 4. Integrate and revalidate

In the original checkout, merge filters, then favorites. Have the integrator wire the components using the frozen props. If a merge conflicts, inspect and resolve it; git merge --abort returns to the pre-merge state if you choose to stop.

```sh
git merge --no-ff feat/filters
git merge --no-ff feat/favorites
# Wire the reviewed components in App.tsx, then:
npm run check
npm run test:e2e
git add .
git commit -m "Integrate filters and favorites"
git tag checkpoint-05
```

## Editable task prompt

```text
You are worker A on feat/filters. Confirm your working directory and branch. Read the frozen interface in docs/plan.md. Implement title search plus room filtering with AND semantics. Own only src/features/Filters.tsx, src/filter.ts and its test. Do not edit App.tsx, shared types, domain rules, package files or the lockfile. Do not create subagents. Run relevant checks. Return changed files, acceptance evidence, assumptions, and the exact parent wiring the integrator must perform. Stop before merging or pushing.

Worker B adaptation: own only src/features/Favorites.tsx, src/favorites.ts and its test; implement favorite toggling and a favorites-only control using the frozen props. Follow the same boundaries and return format.
```

## Evidence

- Each worker actually ran in a different checkout/branch, or the sequential fallback is recorded.
- The change list respects file ownership; one integrator resolves shared wiring.
- Combined title/room/favorites filtering works and earlier agenda guarantees still pass.
- The integrated result is committed before the next experiment.

## Experiment

Ask a worker what it would do if its task requires changing a frozen prop. It should return an interface-change proposal to the integrator. Do not let both workers independently change the same contract. If time remains, change one prop deliberately and resolve the integration test failure.

## Recovery

Do not force a second agent if the laptop struggles. Run A then B in their worktrees, or have one pair member handle each branch on separate laptops. If a worker edited shared files, ask it to return a patch proposal for the integrator rather than blindly merging.
