# 07 · Review a real defect and automate validation

11:20–11:40 · 20 minutes

Find and repair a plausible bug, add regression evidence, and create a CI-backed review packet.

## Concepts

Testing checks specific claims; review looks for failures the current checks may miss. A separate reviewer context helps, but it is not a guarantee of independence or correctness.

A useful review finding names a file, a failing scenario, impact and a verification step. “Improve error handling” is not an actionable finding without a concrete trigger.

The gate fails when a required check fails or was not run. Documentation and check summaries must describe the actual current behaviour, including browser-local persistence and the absence of reservations.

## Understand before building

### Review finding versus opinion

A useful review finding identifies a concrete defect, where it occurs, who it affects and how to reproduce it. A fresh conversation can reduce anchoring on the implementation chat, but does not guarantee a correct review.

```text
Finding: back-to-back sessions rejected.
Trigger: select 09:00–09:30, then 09:30–10:00.
Impact: valid agenda cannot be created; violates AC3.
Evidence: regression fails when < becomes <=.
```

Give the reviewer a known base and diff. Ask it to review before editing, then independently run the reproduction. Reject unsupported findings instead of implementing every suggestion.

**Check your understanding:** Is “improve error handling” enough to accept a finding?

**Expected reasoning:** No. Ask for a specific trigger, impact and verification.

### Regression tests and a failing gate

A regression test preserves a behaviour that a defect broke. First show it fails with the defect present, then passes after the smallest repair. If the test already exists and catches the planted defect immediately, keep it: that is effective coverage.

```text
Correct: a.startMinute < b.endMinute
Defect:  a.startMinute <= b.endMinute
Boundary: one ends exactly when the other begins
```

Use a disposable change and restore it before release. If a new test passes while the defect remains, it has not demonstrated that regression. Do not edit assertions simply to force a green result.

**Check your understanding:** What proves the gate can reject something?

**Expected reasoning:** A known-bad candidate produces a real nonzero check, followed by a checked repair.

### CI, pull request and release evidence

Continuous integration runs checks in a separate runner when the workflow is triggered. A pull request presents a branch change for review. A local green run does not establish remote CI success. A required-check policy needs repository configuration; a YAML file alone does not block every merge.

```text
.github/workflows/ci.yml → install from lockfile → typecheck
→ unit tests → production build → browser tests (one worker)
docs/pr-summary.md → problem, behaviour, checks, limits
docs/release-evidence.md → SHA and actual results
```

Inspect package scripts and workflow triggers. Open a draft PR only in your own correctly identified repository. If remote access is absent, keep a local review packet and label remote CI NOT RUN. Pending is not passed.

**Check your understanding:** Can a README say cloud sync because reload works?

**Expected reasoning:** No. Browser-local persistence is a different capability; review the documentation claims too.

## Steps

### 1. Reproduce a boundary defect

Use a disposable local branch to try the supplied defective condition <= in place of <. If a relevant regression test already exists, show it failing immediately; that is good coverage. Restore the correct implementation before integrating anything. The packet includes a separately named buggy example for review practice.

### 2. Request an evidence-based review

Use a fresh conversation or the client review interface. Supply the base SHA and diff. The agent reviews without edits first. For each finding, require severity, file/line, reproduction, user impact and a suggested check. Validate the finding before accepting a patch.

```sh
git diff checkpoint-05...HEAD
git diff --check
npm run typecheck
npm test
npm run build
npm run test:e2e
```

### 3. Add the CI gate

Use the provided GitHub Actions template. Confirm package.json has real scripts. Do not disable a failing test, replace checks with echo statements, or allow the gate to ignore nonzero exits. The instructor demonstrates a failing gate followed by a fix.

### 4. Prepare the review packet

Write setup, scope, known limitations and recovery steps in README.md. Write docs/release-evidence.md with commit SHA, commands, results and browser evidence. Save docs/pr-summary.md around the final behaviour, not the conversation history.

Publish main as the reviewed baseline and the current experiment/export branch as the candidate, then open the draft PR. Inspect remote CI; pending is not passed. If your branch or remote differs, adapt the commands instead of copying blindly. Without GitHub access, retain the local diff and PR summary and label remote review/CI NOT RUN.

## Editable task prompt

```text
Review the current change against checkpoint-05 without editing first. Prioritise correctness and regressions in overlap handling, corrupt storage, composed filters, exports and accessibility. Return only actionable findings with file/line, trigger, impact, acceptance ID and reproduction. Distinguish confirmed findings from suspicions. Do not invent test output. After I choose a confirmed finding, add a failing regression, implement the smallest fix, run checks, and update release evidence and README to match actual capabilities.
```

## Evidence

- A concrete defect has a demonstrated failing case and a passing regression after repair.
- A clean validation run executes all required scripts; missing or blocked checks are recorded.
- CI configuration and a reviewable diff are present; if pushed, CI status is checked separately.
- README and review summary accurately state browser-local storage and fictional availability.

## Experiment

Temporarily add a change that makes a required check fail. Does the release-check Skill report failure? Does CI stop? Restore the correct code and keep the regression test. A working gate must reject at least one known-bad candidate.

## Recovery

If no reviewer finding is valid, use the packet’s deliberately faulty overlap example and add a new boundary assertion. If CI cannot run remotely, execute the equivalent local commands and mark remote CI NOT RUN; do not fake a green badge.
