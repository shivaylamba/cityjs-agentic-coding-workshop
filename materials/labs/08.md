# 08 · Deploy a candidate and verify the hosted app

11:40–11:55 · 15 minutes

Create a preview deployment, test the hosted journey, and make a separate production decision.

## Concepts

Deployment changes the environment. A local build passing does not prove that assets, storage, routes or downloads behave correctly on the deployed origin.

Release evidence ties a candidate to a commit and a URL. A previous successful deploy is not evidence for a newer unverified commit.

Our deliverable is a release-ready demo with a stated boundary. A genuine production conference system would additionally need durable backend data, authentication where needed, monitoring, privacy review, load testing and an operational owner.

## Understand before building

### Build, preview and production

A build creates assets. Local preview serves those assets on your machine. A hosted preview publishes a candidate URL in the hosting environment. Production publication selects a public release. Success at one stage does not automatically establish success at the next.

```text
npm run build      # create assets
npm run preview    # serve built assets locally
vercel             # hosted preview; inspect project/team
vercel --prod      # only after an explicit release decision
```

Run commands from your own app folder. For this Vite app the built output is dist. The application needs no model credentials. Verify the account and project prompts rather than accepting an unintended destination.

**Check your understanding:** Is an npm run preview URL a hosted deployment?

**Expected reasoning:** No. It is a local check of built assets.

### Candidate identity and hosted smoke tests

A candidate is the specific code being evaluated. A commit SHA identifies committed source; dirty changes mean it is not fully represented by that commit. Smoke tests check critical behaviour on the actual deployed URL.

```text
Record: clean candidate SHA + preview URL + CI status
Observe: add / reject / consecutive / reload / filters / export
Check: keyboard / 390px width / console and network errors
```

Commit and check the intended candidate before deployment. Repeat the critical journey on the exact URL returned. Record observations and failures, not the assumption that local behaviour carried over.

**Check your understanding:** What if the source changes after the checks?

**Expected reasoning:** Validate the affected changed candidate again and update its identity in the evidence report.

### Storage origin, limitations and rollback

A browser origin includes scheme, hostname and port. A new preview URL, profile or private context can have a different storage area. An empty agenda there is expected, not proof that persistence broke. Rollback restores an earlier deployment; it does not reverse every possible external side effect.

```text
localhost origin ≠ hosted preview origin
Browser A storage ≠ private browser storage
Release record: SHA, URL, time, results, limits, previous good deployment
```

This app has no backend side effects, accounts or cloud sync. Keep the previous good deployment identifier and use your hosting dashboard if rollback is needed. A real production system requires more operational engineering than this demo.

**Check your understanding:** If hosting login fails, what is the honest final status?

**Expected reasoning:** Locally verified, not deployed; show the instructor demo without claiming your own hosted checks passed.

## Steps

### 1. Check the candidate identity

Review the diff and working tree. Commit the candidate, run the gate and record its SHA. If the working tree changes after checking, validate the changed candidate again.

```sh
git status --short
npm run check
npm run test:e2e
git rev-parse HEAD
```

### 2. Create a preview in the correct account

Vercel login and installation are prework. From the project folder run vercel and inspect its project/team prompts. Select Vite and dist if configuration is requested. A deployment URL alone does not prove the smoke checks passed.

```sh
vercel
# After hosted smoke checks and your explicit release decision:
vercel --prod
```

### 3. Run the hosted smoke checklist

On the actual preview URL: add; reject overlap; allow back-to-back; reload; compose filters and favorites; export; navigate by keyboard; test at 390px width; check console/network errors. Open a fresh private browser context to confirm a separate empty local agenda.

### 4. Record and release deliberately

Save candidate SHA, deployed URL, deployment time, smoke results, CI status and remaining limitations. If production is published, rerun the critical journey on that URL. Keep the previous good deployment identifier and use your hosting dashboard to roll back if needed.

## Editable task prompt

```text
Prepare a release decision from the current committed candidate. Run the release-check workflow, identify the exact SHA, and report passed, failed and unrun checks. Prepare the Vercel preview steps and a hosted smoke checklist. Do not deploy, push or promote production unless I explicitly authorise that action for the named project. After I provide the deployed URL, compare hosted behaviour with the acceptance criteria and record observed evidence, not assumed results.
```

## Evidence

- The report identifies the checked commit, hosted URL and actual smoke-test results.
- Hosted add/reject/reload/filter/export journeys work on the deployed origin.
- Production publication, if chosen, is a distinct recorded decision and is checked again.
- A hosting/account blocker is labelled “locally verified, not deployed,” not successful release.

## Experiment

Use a new private browser context or another device. Explain why its agenda is empty even though the first browser had saved sessions. Then inspect one missing-asset or stale-build failure and discuss which release check would catch it.

## Recovery

If hosting login or networking fails, use npm run preview and record LOCAL ONLY. Follow the instructor’s hosted demo without claiming your own deployment passed. The remaining five minutes are for questions, not emergency account provisioning.
